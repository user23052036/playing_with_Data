# Architecture & Internals (concise)

## Concept — cluster, database, schema, table

* **Cluster**: one PostgreSQL server instance (data directory) managing multiple databases.
* **Database**: namespace containing schemas, tables, functions.
* **Schema**: logical namespace inside a database (default: `public`). Use schemas to separate modules (`app`, `analytics`).
* **Table**: stores rows and columns.

## Process model

* PostgreSQL is **process-based**: each connection gets its own server process. Implication: connection pooling (PgBouncer) is common in production.

## MVCC (high-level)

* Multi-Version Concurrency Control: updates/deletes create new row versions. Readers don’t block writers and vice versa. Old versions remain until vacuumed.
* **Vacuum / autovacuum** required; long-running transactions prevent vacuum cleanup → **table bloat**.

## WAL (Write-Ahead Log)

* WAL holds changes for crash recovery and replication. Large transactions produce large WAL.

## Interview traps

* Q: Why use connection pooling with Postgres? A: process model + memory per connection.
* Q: What happens to a row on UPDATE? A: New version created; old version persists until vacuum.

# Data Types (practical)

## Numeric

* `smallint`, `integer`, `bigint`, `decimal`
* `numeric(precision,scale)` for exact decimals (money)
* `real`,`float`, `double precision` for floats

## Serial / Identity (auto-increment)

* Legacy: `SERIAL` / `BIGSERIAL` (creates sequence + default)
* Standard & recommended:

```sql
id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY;
```

**Why prefer IDENTITY?** cleaner SQL-standard behavior; fewer stray sequences.

## Character

* `text` (unlimited), `varchar(n)`, `char(n)`
* Prefer `text` unless business needs length limit. Use `citext` extension for case-insensitive text.

## Boolean

* `boolean` (`TRUE` / `FALSE`)

## Date/time

* `date`, `time`, `timestamp` vs `timestamptz` (timestamp with time zone). Prefer `timestamptz` for global apps.

## JSON / JSONB

* `json` stores raw text, `jsonb` stores binary parsed representation (indexed and faster for queries). Use `jsonb` for querying/indexing.

## Arrays, UUID, BYTEA

* Native arrays: `integer[]`, `text[]`
* `uuid` type (use `gen_random_uuid()` from `pgcrypto`)
* `bytea` for binary data

## Interview traps

* Q: `json` vs `jsonb`? A: `jsonb` is query/index friendly; `json` preserves formatting.
* Q: `SERIAL` cleanup? A: sequence remains unless dropped; `IDENTITY` avoids leftover sequence artifacts.

# DDL — CREATE / ALTER / DROP / TRUNCATE

## CREATE TABLE — Concept & syntax

**Concept:** Declare table, columns, constraints.
**Syntax:**

```sql
CREATE TABLE schema.table_name (
  column_name data_type [column_constraint ...],
  [table_constraint ...]
);
```

**Example (recommended):**

```sql
CREATE TABLE public.students (
  id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL,
  email TEXT UNIQUE,
  age INTEGER CHECK (age > 0),
  created_at TIMESTAMPTZ DEFAULT now()
);
```

## ALTER TABLE common ops

* Add column:

```sql
ALTER TABLE students ADD COLUMN phone TEXT;
```

* Alter type (safe pattern using USING):

```sql
ALTER TABLE students ALTER COLUMN age TYPE smallint USING age::smallint;
```

* Set/drop default:

```sql
ALTER TABLE students ALTER COLUMN created_at SET DEFAULT now();
ALTER TABLE students ALTER COLUMN created_at DROP DEFAULT;
```

* Rename:

```sql
ALTER TABLE students RENAME COLUMN name TO full_name;
ALTER TABLE students RENAME TO alumni;
```

## DROP / TRUNCATE

* `DROP TABLE t;` removes table and dependent objects.
* `TRUNCATE t RESTART IDENTITY;` fast remove all rows; optionally `CASCADE`. `TRUNCATE` is transactional but beware interactions with foreign keys and concurrent transactions.

## MySQL differences (cheat)

* MySQL: `AUTO_INCREMENT`, `ENGINE=InnoDB`, backticks — invalid in Postgres.
* `MODIFY` is MySQL; use `ALTER COLUMN ... TYPE` in Postgres.

## Interview traps

* Q: Is `SERIAL` a real type? No — it's a pseudo-type that creates a sequence and default.
* Q: Does `ALTER TABLE` lock the table? Yes — altering type may hold an exclusive lock; be careful in production.

# Constraints — actionable

## Primary Key

```sql
id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
-- or multi-column
CONSTRAINT pk_name PRIMARY KEY (col1, col2)
```

* PK implies NOT NULL + UNIQUE.

## Unique

```sql
email TEXT UNIQUE
-- or
UNIQUE (col1, col2)
```

## NOT NULL

```sql
name TEXT NOT NULL
```

## CHECK

```sql
CHECK (age >= 18 AND age <= 100)
```

* Null values pass CHECK unless expression handles NULLs explicitly.

## Foreign Key

```sql
CONSTRAINT fk_city FOREIGN KEY (city_id) REFERENCES cities(id) ON DELETE CASCADE
```

* `ON DELETE`: `NO ACTION` / `CASCADE` / `SET NULL` / `SET DEFAULT` / `RESTRICT`.
* `DEFERRABLE` allowed in Postgres (`DEFERRABLE INITIALLY DEFERRED`) — useful for multi-step inserts/updates. MySQL/InnoDB does not support deferrable constraints.

## Partial and Expression Constraints (Postgres features)

* Partial unique index enforces constraint on subset:

```sql
CREATE UNIQUE INDEX idx_active_user_email ON users(email) WHERE active;
```

## Interview traps

* Q: Difference between `NO ACTION` and `RESTRICT`? Subtle timing difference in enforcement; practical effect similar.
* Q: Why prefer deferrable FK? To allow temporary constraint violation within a transaction when logic requires it.

# DML — INSERT / UPDATE / DELETE / COPY / RETURNING

## INSERT

```sql
INSERT INTO students (name, email, age) VALUES ('Souvik', 's@example.com', 22);
```

**Insert with returning** (Postgres advantage):

```sql
INSERT INTO students (name) VALUES ('A') RETURNING id, created_at;
```

**Use case:** get generated id or computed columns in a single roundtrip.

## INSERT ... SELECT

```sql
INSERT INTO students_archive (id, name)
SELECT id, name FROM students WHERE created_at < now() - interval '1 year';
```

## UPDATE

```sql
UPDATE students SET age = age + 1 WHERE id = 5;
```

**UPDATE returning:**

```sql
UPDATE students SET age = age + 1 WHERE id = 5 RETURNING age;
```

## DELETE

```sql
DELETE FROM students WHERE id = 10 RETURNING id;
```

**Bulk delete caution:** large deletes create WAL and bloat; use `TRUNCATE` if removing all rows or do delete in batches.

## COPY (bulk import/export)

* From server:

```sql
COPY students (id, name, email) FROM '/path/to/file.csv' CSV HEADER;
```

* From client (psql):

```sql
\copy students FROM 'localfile.csv' CSV HEADER;
```

## Transactions

```sql
BEGIN;
-- multiple DML statements
COMMIT;
-- or ROLLBACK;
```

## Use cases & production notes

* Use `RETURNING` to obtain identity values without extra SELECT.
* Use `COPY` for efficient bulk load.

## Interview traps

* Q: How to avoid table bloat when doing many updates? Use VACUUM; consider partitioning or rewrite approach for bulk transforms.
* Q: What does `RETURNING` do? Returns rows modified; reduces roundtrips.

# Joins (incl. SELF JOIN)

## INNER JOIN

```sql
SELECT a.id, b.name
FROM orders a
JOIN customers b ON a.customer_id = b.id;
```

* Returns rows with matching keys on both sides.

## LEFT (LEFT OUTER) JOIN

* Keep all rows from left; NULL for unmatched right.

```sql
SELECT u.id, o.id AS order_id
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;
```

## RIGHT JOIN

* Rare, symmetric to LEFT JOIN with sides swapped. Prefer rewriting as LEFT JOIN.

## FULL OUTER JOIN

* Keep rows from both sides, with NULLs where unmatched. Useful for diffing two datasets.

## CROSS JOIN

* Cartesian product:

```sql
SELECT * FROM colors CROSS JOIN sizes;
```

## USING vs ON

* `USING (col)` shorthand when columns share the same name: `JOIN t2 USING (id)` — `id` appears once in result.

## SELF JOIN

**Concept:** join a table to itself by using aliases — used for hierarchical or pairwise comparisons.

**Example — employees & managers:**

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```

**Use cases**: hierarchical queries, compare rows in same table, find duplicates.

## Performance notes

* Ensure join columns are indexed for large tables.
* Prefer `EXISTS` vs `IN` depending on correlated logic and planner.

## Interview traps

* Q: Why RIGHT JOIN is discouraged? Usually clearer to flip table order and use LEFT JOIN.
* Q: When is FULL OUTER JOIN inefficient? When matching large tables without selective predicates — can produce massive intermediate result.

# Aggregates, GROUP BY, HAVING

## Aggregate functions

* `COUNT()`, `SUM()`, `AVG()`, `MIN()`, `MAX()`, `ARRAY_AGG()`, `STRING_AGG()`, `BOOL_AND/BOOL_OR`.

## GROUP BY

* Any non-aggregated column in select must appear in GROUP BY (or be inside aggregate or part of functional dependency with `GROUP BY` in Postgres 9.1+ with primary key? avoid relying on that).

```sql
SELECT department, COUNT(*) as cnt
FROM employees
GROUP BY department
HAVING COUNT(*) > 10
ORDER BY cnt DESC;
```

## Window functions (brief mention — crucial for interviews)

* `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)`, `RANK()`, `LEAD()`, `LAG()`. (Detailed coverage planned in Phase 2).

## Use cases

* Aggregations per group, top-N per group (window functions are ideal for top-N per group).

## Interview traps

* Q: `HAVING` vs `WHERE`? `WHERE` filters rows before aggregation; `HAVING` filters groups after aggregation.
* Q: How to get top N per group? Use window functions (`ROW_NUMBER()`).

# Subqueries (single-row, multi-row, correlated)

## Single-row subquery (returns single value)

```sql
SELECT name FROM students WHERE id = (SELECT max(id) FROM students);
```

## Multi-row subquery (with IN / ANY / ALL)

```sql
SELECT * FROM students WHERE department_id IN (SELECT id FROM departments WHERE active);
```

* `EXISTS` vs `IN`: `EXISTS` is often better for correlated checks.

## Correlated subquery

* References outer query; evaluated per row:

```sql
SELECT s.*,
  (SELECT COUNT(*) FROM orders o WHERE o.student_id = s.id) AS order_count
FROM students s;
```

## Replace many correlated subqueries with JOINs or aggregates where possible for performance.

## Interview traps

* Q: `IN` with NULLs? Beware: `IN` behaves oddly with NULLs in subquery results; prefer `EXISTS` or ensure NOT NULL.
* Q: When use correlated subquery? When the value depends on outer row; but consider performance.

# MySQL → PostgreSQL Syntax Mapping (practical cheatsheet)

* `AUTO_INCREMENT` → `SERIAL` / `GENERATED AS IDENTITY`
* `INT(11)` → `integer` (width ignored in Postgres)
* `ENGINE=InnoDB` / `CHARSET` → not applicable
* `\``backticks``` → Postgres uses unquoted lowercase or double quotes for delimited identifiers.
* `MODIFY COLUMN` → `ALTER COLUMN ... TYPE` or `ALTER COLUMN ... SET/DROP DEFAULT`
* `NOW()` in both exist; `CURRENT_TIMESTAMP` is standard.
* `LIMIT offset, count` (MySQL) → `LIMIT count OFFSET offset` (Postgres).
* `IFNULL(x,y)` (MySQL) → `COALESCE(x,y)` (Postgres).
* `NVL` (Oracle) → `COALESCE`.
* `ROWNUM` (Oracle) → use `ROW_NUMBER()` or `LIMIT`.
* `GROUP_CONCAT()` (MySQL) → `STRING_AGG(expr, delimiter)` (Postgres).
* `JSON` functions differ; prefer `jsonb` and operators like `->`, `->>`, `#>` etc.
* `REPLACE INTO` (MySQL) → `INSERT ... ON CONFLICT ... DO UPDATE` (Postgres upsert).

**Upsert example (Postgres):**

```sql
INSERT INTO t (id, val) VALUES (1, 'x')
ON CONFLICT (id) DO UPDATE SET val = EXCLUDED.val;
```

# Exercises — interview-style (with answers)

> Level: Intermediate — focuses on concepts from Phase 1.

## Q1 — Employee-manager list (self join)

**Problem:** Return employee name with their manager name (NULL if no manager). Table `employees(id, name, manager_id)`.
**Answer:**

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```

**Why LEFT JOIN?** Some employees may not have a manager → keep them.

---

## Q2 — Top salary per department

**Problem:** For `employees(id, name, dept_id, salary)`, return one row per department with employee having max salary. If tie, return all ties.
**Answer (using window functions; brief):**

```sql
SELECT id, name, dept_id, salary FROM (
  SELECT e.*,
         RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) as rnk
  FROM employees e
) t
WHERE rnk = 1;
```

**Note:** Window functions are preferable to correlated subqueries for top-N per group.

---

## Q3 — Upsert (insert or update)

**Problem:** Insert `(id, email)` into `users`; if `id` exists, update `email`.
**Answer:**

```sql
INSERT INTO users (id, email) VALUES (1, 'a@x.com')
ON CONFLICT (id) DO UPDATE SET email = EXCLUDED.email;
```

**Interview trap:** `REPLACE` (MySQL) deletes and reinserts → different semantics.

---

## Q4 — Convert NVL to Postgres

**Problem:** Oracle: `NVL(first_name, 'Unknown')`. Equivalent in Postgres?
**Answer:**

```sql
COALESCE(first_name, 'Unknown')
```

**Note:** `COALESCE` accepts multiple args; returns first non-null.

---

## Q5 — Delete duplicates while keeping lowest id

**Problem:** Table `users(id, email, name)` may have duplicate emails. Remove duplicates keeping the row with smallest `id`.
**Answer:**

```sql
DELETE FROM users u
USING (
  SELECT email, MIN(id) AS keep_id
  FROM users
  GROUP BY email
) s
WHERE u.email = s.email
  AND u.id <> s.keep_id;
```

**Alternative:** Use `CTE` with `ROW_NUMBER()`.
